# 请求频率与异常停机

这些限制用于减少请求量、阻止异常后的连续访问，不是平台公布的安全额度，也不保证账号不会受限。没有使用真实账号反复试探平台阈值。

## 请求内容

- 日常监控：每位博主每轮只用 curl GET 主页源码；不翻页、不逐篇请求文章详情。
- 分享链接：逐跳解析，最多 6 跳，每一跳都经过同一个限频入口；Cookie 只发给允许的官方域名。链接预览已核验的资料在 5 分钟内确认添加时直接复用，不重复请求主页。
- 名称搜索：现有用户搜索 POST，第一页、每页 20 个候选；搜索没有自动翻页或自动重试。
- 会话验证：复用主页解析；没有博主时读取官方发现页。同一时间最多一个验证任务，自动成功验证间隔至少 5 分钟。
- User-Agent 在登录窗口和 curl 中保持一致，不随机轮换。声明 HTML/JSON 接收类型、中文语言及 curl 支持的压缩格式。没有伪造浏览器指纹、代理轮换或验证码绕过。
- curl 使用 `-q --config -`，忽略外部 curlrc，避免其添加隐藏重试或自动跳转；连接超时 10 秒、单次最大 25 秒，不启用自动重试，不关闭 TLS 校验。

## 统一限制

| 项目 | 行为 |
| --- | --- |
| 博主计划 | 继续按用户设置的基础间隔 ± 浮动逐轮随机；浮动为 0 时该层计划固定 |
| 所有 curl 请求 | 共用串行队列，上一次结束后再等待随机 30～90 秒；监控、搜索、短链接、验证均覆盖 |
| 同一博主主页 | 距离上次实际请求至少 5 分钟；比此更短的设置会受限频保护约束 |
| 同一其他资源 | 至少 1 分钟；显式会话验证至少 5 分钟 |
| 总请求预算 | 滚动 1 小时最多 60 次、滚动 24 小时最多 500 次；失败尝试、短链接跳转也计入 |
| 手动按钮 | 不绕过最小间隔、总量预算或平台冷却 |
| HTTP 429 / 频次异常 | 至少冷却 30 分钟，重复限流指数增加，最长本地退避 6 小时，额外随机 0～10 分钟 |
| Retry-After | 采用服务端给定秒数或 HTTP 日期；服务端要求更长时不被本地上限缩短 |
| 网络故障 / HTTP 5xx | 全局退避，起始分别为 1 / 5 分钟，重复失败逐步增加，另加随机等待 |
| 账号异常 / 客户端异常 / 验证码 / 登录失效 | 停止全部 curl 业务；搜索触发也联动停止监控，不自动重复登录 |
| 重启 | 请求计数、资源间隔、全局冷却和阻断状态保存到本地 JSON，重启不清零 |

出现账号异常后，先在官方客户端确认账号状态。软件不会自动试探恢复；手动“验证会话”只允许一次受限频保护的验证，通过后才解除阻断。成功响应本身不会让其他采集自动越过账号阻断。curl 返回的 Cookie 轮换会保存，但不再触发额外的自动会话请求。

GitHub 更新检查请求不使用小红书 Cookie，仍单独每小时检查一次。内嵌登录/主页窗口由官方页面自行发起的请求不在 curl 队列内；上述数字仅统计程序发起的 curl 请求。

## 诊断记录

`data/state.json` 的 `requestPolicy` 保存限制状态。`data/logs/curl-requests.jsonl` 仅记录请求时间、耗时、主页/搜索/分享/会话分类、官方主机名、响应状态及下一次允许时间。日志不保存完整 URL、用户 ID、搜索词、请求签名、Cookie 或响应正文。单文件超过 1 MiB 时轮换，只保留当前和上一份。

旧版没有完整请求流水，因此不能仅根据最后一次检测时间还原历史总量或认定账号异常原因。

参考：[HTTP Retry-After 语义](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)、[curl 参数文档](https://curl.se/docs/manpage.html)。
